## What the lead said (2026-10-28)

- An event stream exists to populate an aggregate.
- Async: a promise is like a DMV ticket; most code waits for async calls; async is not pure.
- The domain understands the **structure** of a price but not the price **source**.
- "You can't test the URL, you test the interface." You need to know how to design the interfaces.
- "You do not own prices."
- Identify an aggregate by three questions: 1) who is it built for? 2) what is important to them? 3) what is the invariant?
- For the account, the point is to **have a balance at all**, so you can do something with it, not "balance > 0".
- No such thing as a correct event.
- The code is an enforcer. Creating an entity: if I don't have an aggregate, I don't have a product.
- The rules are protected by the noun. The noun protects the invariant.
- Invariants can be wrong, and that is fine, because you can implement them anyway. The main point: **is fixing easy?**
- Homework: draw the hexagonal architecture.

## 1. What this confirms about the price work

- `PriceSource` as an interface in the domain is the right placement: the domain knows the shape of a price (`priceCents` on an order and on a trade event) and nothing about where it comes from.
- Not unit-testing the Alpaca plug is right: infrastructure is proven through the interface. `FixedPriceSource` is a second plug for the same socket, not a mock, and the command tests run against it.
- "You do not own prices" is the reason there is no `prices` event stream (see the 2026-10-28 summary).
- `async` stops at the app layer. The verbs never see a promise.

## 2. What it changes about how to think of the aggregate

The three questions, answered for `Account`:

1. **Who:** the one user trading on paper.
2. **What matters:** they can deposit, buy, sell, and see where they stand.
3. **Invariant:** the balance and the holdings are one consistent snapshot, so "enough cash" and "enough shares" are enforced against the same state.

The invariant is not "cash above zero". That is one *rule* the aggregate enforces, and rules can be wrong. The reason the aggregate exists is that without it there is nothing to act on: no balance, no product.

"Is fixing easy?" is the design criterion. It is why aggregates stay small, events are never deleted, mistakes become compensating events, and folds can be changed. A design is judged by the cost of being wrong, not by being right the first time. "No such thing as a correct event" belongs with it: an event is what happened; correctness lives in the rules that decide the next event, and those can be fixed.

## 3. The hexagonal picture — `docs/hexagonal.svg`

Inside out:

- **Centre (green):** the domain. Aggregate, four events, fold, verbs. No clock, no ids, no I/O, no promises.
- **Ring (purple):** the app layer, the commands. Wraps the domain; the only thing that touches the sockets; where async stops.
- **Sockets on the edge:** the command functions themselves (what the outside calls), `EventStore` and `PriceSource` (what the core calls). Both declared in `domain/` as pure types.
- **Plugs outside:** left, who calls in — the UI through HTTP, and the tests calling the same functions. Right, what the core calls out to — two plugs per socket, arrows pointing at the socket: *implements*.
- **Read side (orange):** the projection reads events through the store socket and builds the report table. Outside the hexagon on purpose: not part of the aggregate, no verb protects it.
- **Bottom (amber):** `main.ts`, the only file that knows which plug goes into which socket.

The thing to point at: every arrow from the right crosses the edge through a socket, and nothing inside the green area has an arrow leaving it.

## 4. Portfolio summary — a reporting query

"What is my portfolio worth and what have I made" is a question about state. Nothing happened in the business, so there is no event and no verb; it is the read side.

Two legitimate ways on the read side: fold the events again in a pure function, or `SUM` over the `positions_report` table. The second was chosen because it shows CQRS doing its job — the table was built so that this question is one SQL statement.

- `SqlPositionsReport.summary()`:
  - `investedCents` = `SUM(quantity * avg_cost_cents)` over open rows (cost basis of what is held)
  - `realizedPnlCents` = `SUM(realized_pnl_cents)` over all rows, closed ones included
  - `openPositions` = `COUNT` of rows with quantity > 0
- `GET /api/summary` adds `cashCents` from the account view and returns one object.
- A summary row in the UI above the positions report.
- Two tests on the SQL: sums against hand-built events with one closed position; zeros on an empty report.

Deliberately absent: market value and unrealized P&L. They need current prices in the report, which is the valuation step.

Checked live: invested equals the sum of the cost-basis column, realized equals the sum of the realized column.

## 5. Small additions considered for the price connector (not built)

1. `CachedPriceSource`: a plug that wraps a plug, remembers answers for ~30 s with an injected clock. Cuts Alpaca calls; shows decoration of a socket without the core noticing. ~20 lines.
2. The price's own timestamp: Alpaca returns when the trade happened; the socket could return `{ priceCents, asOf }` so a Friday close is not shown as live. Changes the interface — "you need to know how to design the interfaces".
3. Valuation in the positions report: market value and unrealized P&L per held symbol, fetched on read, one failing symbol does not stop the others, stale prices show their age. Builds on 2.

## 6. Why `FixedPriceSource` exists (asked and answered)

Mainly for tests: commands need a price to attach to an order, and tests must be fast, repeatable and offline. Alpaca gives a different number every second and fails without the network. Secondarily so the app starts without keys. Deeper: an interface with one implementation is a formality; the moment a second plug fits the same socket and the commands cannot tell which one they hold, the inversion is real.
