# 2026-10-19 — business verbs, one event shape, StockBought, positions report, UI, first tests

## What the lead said (2026-10-17)

- Events are moment-focused. `at` is when it happened, not "now", so the business function takes it as an argument. Passing time in is the one accepted break of the purity rule; tests deal with it by passing a fixed value.
- A deciding function always takes the aggregate as an argument, usually first. It needs: what account, how much, what time.
- Verb strategy, not noun strategy. Functions are present-tense business verbs (`collectDeposit`, `sendWithdrawal`), events are past-tense facts (`DepositCollected`, `WithdrawalSent`). Not `decideDeposit`: the event would be `DepositDecided`, which means nothing. Names should sound like what a business user would say. Not `updateMachine` but `MachineReturned`.
- Commands can be unit tested with fake arguments; `account.ts` is pure unit tested.
- Transactions plan approved: schema, fold branch, `buyStock(account, input)`, `buy(deps, input)` same four lines as withdraw.
- Biggest real-world problems: off-by-one errors and naming things.

## 1. Business verbs and one event shape

| Before | After |
|---|---|
| `decideDeposit`, `decideWithdrawal` | `collectDeposit`, `sendWithdrawal`, `buyStock` |
| `'DepositMade'`, `'WithdrawalMade'` | `'DepositCollected'`, `'WithdrawalSent'`, `'StockBought'` |
| intents + events, `Omit`, store mints id and time | one event shape; the verb returns a complete event |
| store held `newId` and `now` | `Deps` holds `now` and `newId`; the command hands both to the verb |

Every verb has the same signature: `(account, input, now, id) => Result<Event>`.
The aggregate first, the business input, the time, a fresh id. The id is
passed in for the same reason the time is: the domain cannot mint either, and
`account.id` cannot be used because it names the stream and every event needs
its own. The store stores exactly what it is given.

The intent layer was removed. It existed only so the store could mint the id;
once the id is an argument, one shape is enough.

## 2. Naming cleanup

- `BuyInput` → `StockOrder`. "Input" is a technical word; an order is what you give a broker, it may be refused, and `sellStock` will reuse it unchanged.
- `Instrument`, `INSTRUMENTS`, `isKnownSymbol` → `Stock`, `STOCKS`, `isKnownStock`. The project trades stocks only; one word everywhere. (`CONSTS` was considered and rejected: it names the kind of variable, not what it holds.)
- Command names match their verbs: `deposit` → `collectDeposit`, `withdraw` → `sendWithdrawal`, `buy` → `buyStock`. `addStockShares` was rejected as noun thinking.

## 3. StockBought

`StockBoughtSchema = AccountEventBase.extend({ type, symbol, quantity, priceCents })`,
added to the union. `buyStock` guards in order: known stock, whole positive
quantity, whole positive price, cost within cash.

The fold gained one line: a buy subtracts `quantity * priceCents`. It does
**not** track positions, because no rule needs them yet. "Cannot sell what
you do not hold" is the first rule that will, and that is when `positions`
joins the fold. Until then, protecting them would be a fake invariant.

One business fact, one event. The cash leaving is a consequence computed by
the fold, not a second `CostSent` event. Two events for one buy would be the
dual-write problem inside one aggregate.

Price is typed by the user. It is not in `STOCKS`: a stock's identity is
reference data, its price is market data that changes every second. Pulled
prices come later as a `prices` stream behind a `QuoteSource` socket, with a
fixed-price fake for demos.

## 4. Positions report (first read model)

`src/projections/positionsReport.ts`:

- `positionsFrom(events): Position[]` — pure. Buys of the same symbol are
  averaged: `avg = (oldQty * oldAvg + qty * price) / newQty`, rounded.
- `SqlPositionsReport` on its own file, `data/reports.sqlite`.
  `rebuild(events)` wipes and refills from the pure function; `list()` reads.

Rebuild-from-scratch is the simplest correct projector. Incremental
checkpoints come when the stream is long enough to need them.

Why the folder is called `projections`: projecting is the act of turning
events into a table shaped for reading. The file holds the projector and the
one query over its result. If the read side grows, queries move to their own
folder.

## 5. HTTP and UI

`src/http/app.ts`: three write routes (`/api/deposits`, `/api/withdrawals`,
`/api/orders`), four read routes (`/api/events`, `/api/account`,
`/api/positions`, `/api/stocks`), one `reply` translator from `Result` to
HTTP. Request bodies go through zod `safeParse`: the second place data comes
from outside the world, and the non-throwing form because a bad body is a
user error, not a bug.

`public/index.html`: cash, buy stock (dropdown of the ten stocks), positions
report, event stream newest first. `npm run dev`, then http://localhost:3000.

Two shortcuts to name in review:
- `GET /api/positions` rebuilds the report on every read.
- `GET /api/events` reads the store directly for the UI's list. The clean
  version is a third projection.

## 6. Tests, no mocks

`npm test` (all) or `npx tsx --test tests/account.test.ts` (one file). 13 tests.

- `tests/account.test.ts`: `collectDeposit` and `sendWithdrawal`, pure. Fixed
  `at` and `id` at the top; hand-built accounts; one `describe` per function,
  one `it` per rule, named as a business sentence; `deepEqual` on the whole
  event so a wrong `type` or missing field fails loudly; the boundary tested
  from both sides (exactly the balance passes, one cent more fails); guard
  order tested (a bad amount is refused for being bad, not for exceeding cash).
- `tests/positionsReport.test.ts`: `positionsFrom` on hand-written events,
  the fold with a buy, `buyStock` happy and refused paths, and the SQL report
  fed through the real store on `:memory:`.

`tsconfig.json` now includes `tests` so the editor type-checks them.
