# 2026-10-15 — zod layers, one read, folders, reference data, next: transactions

## What the lead said (2026-10-15)

- Mocking is problematic, hard and bad. Test the intent of behaviour, not how it is done.
- "My append is just an idea, not what I do to the database." The decide/append split couples well with functional programming.
- Folders would help to organise.
- In JS everything is a JSON object; you cannot run a runtime check if you do not know the type. Use zod only where data comes from outside the world, not everywhere.
- `accountBalance` folds events, so rename it.
- You always read all events; the fold is the one place to go when adding fields to the aggregate.
- Events vs StoredEvents was a good idea, badly implemented. All logic should work on stored events. Do "real TS": use the type system, generics, one consistent event shape.

## 1. zod: two layers, intents and events

The schemas written with the lead stay as they are. They describe a deposit and
a withdrawal *without* an envelope. That is exactly what a decide function
returns, so they got the name they deserved:

```ts
const DepositSchema    = z.object({ type: z.literal('DepositMade'),    amountCents: z.number().int().positive() });
const WithdrawalSchema = z.object({ type: z.literal('WithdrawalMade'), amountCents: z.number().int().positive() });
const AccountIntentSchema = z.discriminatedUnion('type', [DepositSchema, WithdrawalSchema]);
type AccountIntent = z.infer<typeof AccountIntentSchema>;
```

An **intent** is "the idea": `decideDeposit` says *a deposit of 20000 should
happen* and nothing more. No id, no time, because a pure function cannot
mint either.

The second layer is the lead's V2 interfaces, written in zod. `extends` on an
interface is `.extend()` on a schema:

```ts
const AccountEventBase = z.object({ id: z.string(), at: z.string(), type: z.string() });
const DepositEventSchema    = AccountEventBase.extend({ type: z.literal('DepositMade'),    amountCents: ... });
const WithdrawalEventSchema = AccountEventBase.extend({ type: z.literal('WithdrawalMade'), amountCents: ... });
const AccountEventSchema = z.discriminatedUnion('type', [DepositEventSchema, WithdrawalEventSchema]);
type AccountEvent = z.infer<typeof AccountEventSchema>;
```

An **event** is an intent plus the envelope. `id` and `at` are declared once
in the base and inherited, which is the consistency the lead wanted. `.extend`
narrows `type` from `string` to the literal, so `if (e.type === 'DepositMade')`
still narrows the union.

Every TypeScript type is derived with `z.infer`, so there is one definition
per shape, not two.

Where the two layers meet: `append`. It is the only impure place, so it may
mint:

```ts
const event: AccountEvent = { ...intent, id: this.newId(), at: this.now() };
```

Where zod runs: `read`, and only there. The payload is the one place JSON
crosses from outside the world. The domain trusts its types because the
boundary checked them. A corrupt row throws with the field name; that is a
storage bug, not a user error.

## 2. One `read`

Before: `read` returned bare facts for folds, `readStored` returned
`{ id, at, event }` for the UI. The lead's objection: two parallel shapes, and
logic running on the one without the envelope.

Now: the whole event, envelope included, is the payload. `read` parses it with
`AccountEventSchema` and returns `AccountEvent[]`. The fold takes
`AccountEvent[]` and ignores `id` and `at`. The UI reads the same list. One
shape everywhere, one read. The `id`, `type` and `at` columns keep copies for
lookup and ordering only.

## 3. Folders

```
src/
  domain/account.ts       Result, schemas, types, Account, foldAccountEvents, decideDeposit, decideWithdrawal
  domain/eventStore.ts    the EventStore interface
  domain/instruments.ts   reference data (see 4)
  storage/sqlEventStore.ts  the one impure class
  commands/account.ts     Deps, ACCOUNT_ID, deposit, withdraw
  main.ts                 composition root
```

The import lines are the dependency diagram and point one way:

- `domain` imports nothing of ours.
- `storage` and `commands` import `domain`.
- `main` imports all three.

The `EventStore` interface sits in `domain`, not `storage`, because it is a
pure type (the lead's earlier note). The first cut had `commands` importing it
from `storage`, which would have let the edge leak inward; moving it fixed the
arrow.

Why split at all: each folder has one reason to change. A new SQL engine
touches `storage`. A new rule touches `domain`. A new user action touches
`commands`. `main` changes when wiring changes.

## 4. Reference data: `instruments.ts`

Ten stocks as a constant array plus `isKnownStock`. They are not events: the
business did not produce them, they are facts the app was handed. They are not
stored: nothing about them changes at runtime. They live in `domain` because
`decideBuy` is pure and needs them, and a constant has no side effects.

If the list ever needs to change without a deploy, it becomes a table and a
query, and `decideBuy` receives the check as a function, the way `monthSpentCents`
was injected in the expense app. The decide does not change.

### Why `isKnownStock` returns `boolean`, not `Result`

Three kinds of answer, three shapes:

| Question | Shape | Example |
|---|---|---|
| Can this operation fail, and why? | `Result<T>` | `decideBuy` |
| Is there one of these, or not? | `T \| undefined` | a future `findStock(symbol)` |
| Yes or no? | `boolean` | `isKnownStock` |

`Result` wraps an operation that produces a value or fails with a reason.
A predicate has no value to produce and no failure to explain;
`{ ok: true, value: false }` would read as "succeeded at being false".
The reason belongs one level up, in the decide:

```ts
if (!isKnownSymbol(input.symbol)) return { ok: false, error: `unknown symbol ${input.symbol}` };
```

If `decideBuy` ever needs the instrument's name, the predicate becomes a
lookup, `findStock(symbol): Stock | undefined`. Still not `Result`:
a missing entry in a list is an absence, not a failure.

### `ReturnType<typeof fn>` does not apply here

It derives a type from what a function returns, for factories like
`createAccountService`. `instruments.ts` has no factory. The matching
"derive from the source" trick for data is `as const` plus
`type Instrument = (typeof STOCKS)[number]`, which would make the ten
tickers a literal union the compiler can check. Optional; the interface is fine.

## 5. Plan for transactions

A buy spends cash. "Cash never goes below zero" is the aggregate's one real
invariant, so `StockBought` belongs to the **same** aggregate and the same
stream. No new store, no new stream. The account's state becomes cash plus
positions.

Changes, all in `domain/account.ts` and `commands/account.ts`:

1. `StockBoughtSchema` (`type`, `symbol`, `quantity`, `priceCents`, positive ints) added to `AccountIntentSchema`.
2. `StockBoughtEventSchema = AccountEventBase.extend(...)` added to `AccountEventSchema`.
3. `Position { symbol, quantity, avgCostCents }`; `Account` gains `positions: Position[]`.
4. `foldAccountEvents`: a third branch subtracts the cost from the balance and updates the position (average cost).
5. `decideBuy(account, input): Result<StockBought>`: known symbol, positive whole quantity and price, cost not above balance.
6. `buy(deps, input)`: the same four lines as `withdraw`.

The store, the interface and `main` do not change. That is the test that the
structure is right.

Price is typed by the user for now. Alpaca comes later as its own stream or
report, never inside this aggregate: a price is not something the account did.

## 6. Open for the next review

- Two withdrawals at the same time: `append(stream, expectedSeq, intent)` so a stale read fails instead of appending behind someone's back. Proposed, not built.
- `deposit` and `withdraw` are the same four lines with a different decide. One `apply(deps, decide)` helper, or keep them explicit for readability?
- `foldAccountEvents` returns `Result` for an unknown event type that zod now makes unreachable. Keep for the functional style, or return `Account` directly?
