# 2026-10-14 — review follow-up: aggregate, purity split, readStored, zod

## What the lead said (2026-10-14)

- The `EventStore` interface is a pure type; it belongs with the domain. Only the SQL class is impure.
- An `if` inside a command is business logic leaking into impure code. Keep `decide*` pure; make the command a thin pass-through.
- `at` on every event: tolerated, not loved. Design preference, not a defect.
- `CashEvent` implies an aggregate, and that is right. An aggregate is the representation of an invariant. Do not split it. Name it.
- Two withdrawals at the same time: what happens? Ordering matters. The invariant protects future events. (Open question: expected version on append.)
- Most invariants are fake. Check a rule is a real business rule before protecting it. Consistency vs design is the trade-off to name.
- Reading: Vaughn Vernon, "Effective Aggregate Design" (3 parts), then the red book after the blue book; Eric Evans talks on YouTube.

## What changed in `app/write.ts`

| Before | After |
|---|---|
| events carried `id` and `at` | events are bare facts: `{ type, amountCents }` |
| `decideWithdrawal(id, amountCents, balanceCents, at)` | `decideWithdrawal(account, amountCents)` |
| `cashBalance(events): number` | `accountBalance(id, events): Result<Account>` builds the aggregate |
| `Deps` held `newId` and `now` | the store's constructor takes them; `Deps` is just `{ store }` |
| commands read, folded, decided, checked, appended | commands: read → fold → decide → append, no business `if` |
| one `read` with a cast | `read` for folds, `readStored` for the UI, zod replaces the cast |

## The aggregate

`Account` = `{ id, balanceCents }`, produced by folding the account's stream.
The stream name is the account id (`ACCOUNT_ID = 'main'`). Its one invariant,
balance never below zero, lives in `decideWithdrawal`. Nothing else may append
a withdrawal.

## The purity split

| Pure | Impure |
|---|---|
| `Deposit`, `Withdrawal`, `AccountEvent`, `Account`, `StoredEvent` | `SqlEventStore` (the only class) |
| `accountBalance` (fold) | `randomUUID`, `new Date` — inside the store |
| `decideDeposit`, `decideWithdrawal` | the SQLite connection, opened in `main` |
| the `EventStore` interface | `main` |
| `AccountEventSchema` (a value, no side effects) | |

Commands sit on the line: no rules, only calls to pure functions and one
`append`.

## `read` vs `readStored`

Same SELECT, different slice of the row.

- `read(stream): AccountEvent[]` — the payload only. For folds and decides.
  The domain must never see ids or timestamps; a test of the balance rule
  should not have to invent them.
- `readStored(stream): StoredEvent[]` — `{ id, at, event }`. For the UI. A list
  is unreadable without times, and "reverse this deposit" needs the id of
  the deposit it reverses.

Letter and envelope: the fold reads letters, the screen needs the postmark
and tracking number too.

## zod

`AccountEventSchema` mirrors the two interfaces. `toEvent` runs
`AccountEventSchema.parse(JSON.parse(payload))`; a corrupt row throws with a
precise message instead of producing a wrong balance. See `docs/ZOD.md`.

## Open for next review

1. Two concurrent withdrawals: `append(stream, expectedSeq, event)` so a stale
   read fails instead of appending behind someone's back. Proposed, not built.
2. `deposit` and `withdraw` are the same four lines with a different decide.
   One `apply(deps, decide)` helper, or keep them explicit for readability?
3. `accountBalance` returns `Result` for the unknown-event case. zod now rejects
   those rows before the fold sees them. Keep the `Result`, or let the fold
   return `Account` directly?
