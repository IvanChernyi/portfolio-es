# 2026-10-26 — fold without an id, event arrays, sellStock, positions in the aggregate

## What the lead said (2026-10-24)

- Domain functions should return an **array** of events, not one. A business action may produce several facts (`collectDeposit` → a deposit, and possibly something else). All verbs return the same `AccountEvent` type so they can be chained by left-folding.
- At the app layer: left-fold the stream to get the account, call a verb, fold again with the new events, call the next verb. Repeat as much as you want. Chain deposit, withdrawal, deposit as the proof.
- `foldAccountEvents` should never take an id. The id is in the events; take only the array.
- An aggregate always has an id. `StockOrder` is a value object, not an aggregate. Entities, value objects, aggregates: all aggregates are entities, not all entities are aggregates. An aggregate is a "super entity" that protects business rules. Never an aggregate inside an aggregate.
- An aggregate is a state. Return the JSON object (a simple projection of the account), not just the balance.
- Three layers: domain (business, no tech concerns), app layer (feeds the deps, works through interfaces, no connection to infrastructure), infrastructure (the boring layer, connections to external services).
- Positions report: rebuild from scratch is fine; checkpoints when the stream is long enough.
- Left folding content into an aggregate; right folds are rarely needed.

## 1. The fold takes only events

Before: `foldAccountEvents(id, events)`. The caller told the fold which account it was reading, so the fold could not be trusted on its own.

Now: `foldAccountEvents(events): Result<Account>`. The account id is read from the first event. An empty array cannot produce an account and returns a failure.

For that to work, every event has to name its account. We did it the way it was started with the lead: the event's `id` field **is** the account id. An event no longer has an identity of its own; its identity is its place in the stream, `(stream, seq)`, which was already the table's primary key.

Consequences, both handled:

- The `events` table had `id TEXT NOT NULL UNIQUE`. With the account id on every row, the second insert would have been rejected. The column is now `account TEXT NOT NULL`, no `UNIQUE`.
- Nothing mints ids any more. `newId` left `Deps` and `main`.

Trade-off to name in review: without a per-event id there is no idempotency key, so a retried request appends twice. The answer is an expected `seq` on `append`, already on the open list.

## 2. The empty stream

A fold over zero events has nothing to read an id from, so the first deposit could not get an account. Two possible answers:

- **Minimal (done):** `loadAccount(deps)` in the commands returns a fresh account with zero balance when the stream has no events, otherwise folds. The app layer knows which stream it is reading, so supplying the starting state there is within "the app layer feeds the deps".
- **Proper (to discuss):** an `AccountOpened` event starts every stream, with an `openAccount` verb that is the one verb without an aggregate argument.

`/api/account` uses `loadAccount` too, so the UI shows $0.00 on first run instead of an error.

## 3. Verbs return arrays and take three things

Every business verb is now `(account, input, now) => Result<AccountEvent[]>`:

| Verb | Input | Event |
|---|---|---|
| `collectDeposit` | `amountCents` | `DepositCollected` |
| `sendWithdrawal` | `amountCents` | `WithdrawalSent` |
| `buyStock` | `StockOrder` | `StockBought` |
| `sellStock` | `StockOrder` | `StockSold` |

Today each array holds one event. The shape is fixed now so that a verb that one day produces two facts does not change every signature. The `id` parameter is gone from all of them; the event's `id` is `account.id`.

Commands append the whole array through one `appendAll` helper.

## 4. sellStock and positions in the aggregate

"Cannot sell what you do not hold" is the first rule that needs holdings. So `Position { symbol, quantity, avgCostCents }` moved into the domain and `Account` gained `positions: Position[]`. Until this rule existed, positions lived only in the report, because protecting them would have been a fake invariant.

The fold now tracks positions:

- a buy raises the quantity and recomputes the average cost: `(oldQty * oldAvg + qty * price) / newQty`, rounded;
- a sell lowers the quantity and leaves the average cost alone;
- a position sold to zero drops out of the aggregate.

`sellStock(account, order, now)` reuses `StockOrder`, which is why the name was chosen over `BuyInput`. Guards in order: known stock, whole positive quantity and price, enough shares held.

One business fact, one event. The cash coming back is a consequence computed by the fold, not a second event.

## 5. The report: realized P&L, closed positions kept

`positionsFrom` now handles `StockSold`: realized P&L accumulates as `(sellPrice − avgCost) × quantity`. Rows whose quantity reaches zero **stay** in the report, marked closed, so the profit remains visible.

This is a deliberate difference between the two folds. The aggregate drops a closed position because no rule needs it. The report keeps it because a reader does. The average-cost arithmetic exists in both places: the read side owns its own fold and may compute things the write side does not care about (realized P&L is not an invariant).

Table gained `realized_pnl_cents`. Rebuild-from-scratch stays, as approved.

## 6. HTTP and UI

- `POST /api/orders` takes `side: 'buy' | 'sell'` (zod enum). One order concept, one route; the handler picks `buy` or `sell`.
- `/api/account` returns the whole aggregate, `{ id, balanceCents, positions }`, per "return the JSON object".
- The form is "Trade stock" with Buy and Sell buttons. The report shows a Realized P&L column with closed rows greyed. The event list shows `StockSold`, and its first column is now the position in the stream (`#`) instead of an id, since every event's id is the same account.

## 8. Open for the next review

2. Expected `seq` on `append` for concurrent commands and as the idempotency answer now that events have no own id.
3. `deposit`, `withdraw`, `buy`, `sell` are the same four lines with a different verb. One `apply(deps, verb)` helper, or keep them explicit?
